# Основной пользовательский сценарий

## 1. Запуск приложения

Пользователь открывает mini-app внутри MAX.

Frontend получает данные MAX через `window.WebApp`.

Для авторизации использовать:

```typescript
window.WebApp.initData
```

`initData` отправляется на backend.

Backend:

1. валидирует данные MAX;
2. извлекает `user.id`;
3. ищет пользователя в PostgreSQL;
4. если пользователя нет — автоматически создаёт его;
5. если пользователь существует — обновляет доступные данные профиля;
6. возвращает информацию о пользователе приложению.

Таким образом отдельной регистрации и логина быть не должно.

Основным внешним идентификатором пользователя является:

```text
max_user_id
```

Не использовать `initDataUnsafe` для серверной авторизации.

# Кэширование мероприятий

Для MVP не нужно строить отдельный ETL-сервис или сложный event pipeline.

Можно использовать следующий подход:

1. Backend делает запрос в API «PRO.Культура.РФ».
2. Полученные мероприятия сохраняются/обновляются в PostgreSQL.
3. Пользовательские рекомендации строятся уже на локальных данных.
4. Данные периодически обновляются.

Для хакатона достаточно простого механизма обновления:

```text
GET external API
       |
       v
transform data
       |
       v
UPSERT events
       |
       v
PostgreSQL
```

При необходимости можно сделать endpoint:

```http
POST /api/admin/events/sync
```

или простой background task.

Не нужно использовать Kafka, RabbitMQ, Celery или Redis, если без них можно обойтись.

# 5. Лайк / дизлайк

## Like

Свайп вправо означает:

```text
INTERESTED
```

Мероприятие:

1. добавляется в личный список пользователя;
2. используется для улучшения последующих рекомендаций.

## Dislike

Свайп влево означает:

```text
NOT_INTERESTED
```

Такое мероприятие не должно снова показываться пользователю.

Реакции сохраняются в PostgreSQL.

Пример таблицы:

```text
event_reactions

id
user_id
event_id
reaction
created_at
```

Где:

```text
reaction = like | dislike
```

На уровне БД желательно сделать:

```text
UNIQUE(user_id, event_id)
```

# 6. Рекомендательная система

Для MVP НЕ использовать ML.

Реализовать простую content-based recommendation систему.

Каждому мероприятию вычислять score.

Например:

```text
score =
    category_score
  + city_score
  + price_score
  + date_score
  + liked_categories_score
  - disliked_categories_score
```

Пример логики:

- категория указана в анкете → +3;
- мероприятие находится в выбранном городе → +5;
- цена соответствует бюджету → +2;
- пользователь ранее лайкал эту категорию → +2;
- пользователь часто дизлайкал эту категорию → -2.

Дальше:

```text
ORDER BY score DESC
```

и отдавать пользователю наиболее релевантные мероприятия.

Важно:

пользователь не должен повторно получать мероприятия, на которые уже поставил like/dislike.

Архитектура рекомендаций должна быть такой, чтобы позже алгоритм можно было заменить.

Например:

```python
class RecommendationService:
    def get_recommendations(...)
```

# Важные ограничения

Это проект для хакатона.

При разработке придерживаться следующих принципов:

1. Не переусложнять архитектуру.
2. Не использовать микросервисы.
3. Backend — один FastAPI application.
4. Одна PostgreSQL.
5. Не добавлять Kafka.
6. Не добавлять RabbitMQ.
7. Не добавлять Redis, пока он действительно не требуется.
8. Не создавать отдельный recommendation microservice.
9. Не использовать ML.
10. Не строить сложный DDD/Clean Architecture с десятками слоёв.
11. Разделять API, models, schemas и services в разумных пределах.
12. Все внешние API должны вызываться только backend'ом.
13. Все секреты хранить в environment variables.
14. Делать mobile-first UI.
15. Код должен быть простым и понятным другому разработчику.

Главная цель:

> За минимальное время получить полностью работающий end-to-end MVP, который можно показать жюри.

# Definition of Done

3. пройти анкетирование;
4. получить персональную подборку мероприятий;
5. свайпать мероприятия;
6. поставить like/dislike;
7. посмотреть понравившиеся мероприятия;
8. открыть полную информацию о мероприятии;
9. увидеть место проведения;
10. поделиться мероприятием с другом через MAX;
11. изменить свои предпочтения.
