# Муршрут 🐱

MAX mini-app с персональной афишей. React + Vite + TypeScript + Tailwind + MAX UI → Nginx → FastAPI + SQLAlchemy → PostgreSQL. Без ML и дополнительных сервисов.

## Запуск

```bash
docker compose up --build -d
```

Откройте http://localhost:8080. По умолчанию включён деморежим: ключи не нужны. Демособытия вымышленные, доступны Москва, Санкт-Петербург и Казань. Демо использует один общий демонстрационный профиль; это не многопользовательская авторизация. Данные сохраняются в Docker volume.

```bash
docker compose logs -f backend
docker compose ps
curl http://localhost:8080/api/health
docker compose down
```

## Что работает

- Анкета из трёх шагов: город, интересы, компания, бюджет, дни и время.
- Свайпы вправо/влево и кнопки реакции. Карточка убирается только после сохранения реакции на сервере.
- Подборка пересчитывается после каждой реакции, просмотренные события исключаются.
- В «Открывать» — режимы «Свайпы / Каталог». Каталог показывает также пропущенные события: поиск по названию и площадке, быстрые фильтры, конкретная дата, категории, бюджет и вечернее время.
- Готовые подборки «Бесплатно на выходных», «Вечер в городе», «Выставки и прогулки» применяют обычные фильтры. Сохранение доступно прямо из списка; при возврате из подробностей сохраняются загруженные страницы и прокрутка.
- Сохранённые события, подробности, удаление из избранного, редактирование предпочтений.
- Карта OpenStreetMap с метками избранного или рекомендаций; используются готовые координаты.
- MAX Bridge: серверная авторизация, кнопка «Назад», шеринг текста и deep link `event_<UUID>`.
- В обычном браузере — Web Share API или копирование ссылки. Шеринг вызывается только по нажатию пользователя.
- Кот Мур, загрузка, пустые состояния, ошибки и повторные попытки.

## Реальный MAX и источник мероприятий

Скопируйте `.env.example` в `.env`, укажите:

```env
DEMO_MODE=false
EVENT_PROVIDER=culture
MAX_BOT_TOKEN=<токен вашего бота>
MAX_BOT_NAME=<имя бота из ссылки max.ru>
JWT_SECRET=<случайная строка не короче 32 символов>
POSTGRES_PASSWORD=<свой пароль>
CULTURE_API_KEY=<партнёрский ключ PRO.Культура.РФ>
ADMIN_SYNC_TOKEN=<секрет для ручной синхронизации>
```

Секрет можно создать: `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`.

Перезапустите `docker compose up --build -d`. Для мини-приложения нужен публичный HTTPS URL: настройте TLS на внешнем reverse proxy и привяжите URL к боту на платформе MAX. Локальный Compose обслуживает HTTP, автоматического выпуска сертификата нет.

Авторизация проверяет HMAC-SHA256 по официальному алгоритму MAX (`WebAppData`), уникальность параметров и возраст не более часа. После проверки создаётся/обновляется пользователь по `max_user_id` и выдаётся JWT на 24 часа. JWT находится только в памяти вкладки. Неверные MAX-данные никогда не переключают пользователя на демо. В production demo endpoint отключён, при отсутствии токена или безопасного JWT_SECRET backend не стартует.

### PRO.Культура.РФ

Используется документированный API 2.5: `locales`, `categories?type=events`, `pushkinsCardEvents`. Последний возвращает события, участвующие в «Пушкинской карте» — это ограничение доступной официальной документации, а не вся афиша России. `CULTURE_EVENTS_PATH` можно поменять на другой endpoint, подтверждённый для вашего партнёрского доступа. Реальные запросы требуют партнёрский ключ; без ключа live-интеграция не проверялась.

Город разрешается через локали API культуры (точное совпадение имени). Клиент постранично загружает полный список событий за синхронизацию, выбирает ближайший будущий сеанс и его площадку, преобразует миллисекундные даты, адреса, цены и координаты `[latitude, longitude]`. HTML-описание превращается в обычный текст. ФИАС не требуется: источник уже содержит адрес и координаты. Для изображений используется готовый `image.url`, если он присутствует; при наличии только `image.name` отображается локальная иллюстрация, URL файла не выдумывается. Автор изображения сохраняется.

События обновляются при запросе рекомендаций, не чаще раза в 30 минут для города. Кэш хранится в PostgreSQL. При сбое API используется доступный актуальный кэш; если его нет, показывается ошибка. Демоданные не подмешиваются в production. Все запросы к API культуры и ключи находятся на backend.

Ручная синхронизация:

```bash
curl -X POST 'http://localhost:8080/api/admin/events/sync?city=Москва' \
  -H 'X-Admin-Token: <ADMIN_SYNC_TOKEN>'
```

## Рекомендации

Каталог доступен через авторизованный `GET /api/v1/events/catalog`: `q`, `date_mode=any|today|weekend|date`, `date=YYYY-MM-DD`, повторяемый `categories`, `free_only`, `budget_max`, `time=any|evening`, `limit` (20 по умолчанию, максимум 100), `offset`. Ответ: `{items, total, has_more}`, каждый элемент содержит `is_saved`. Город и источник задаются профилем и конфигурацией сервера. Даты учитывают часовой пояс события и пересечение интервала с выбранным днём; фильтры применяются до пагинации. Сортировка — по началу и ID. При выборе бюджета неизвестная цена исключается, бесплатные события включаются; `free_only` нельзя сочетать с `budget_max`. Поиск воспринимает `%` и `_` буквально. Как и рекомендации, каталог использует актуальный кэш при сбое источника. Фильтры работают по одному сохранённому сеансу, а не полному расписанию события.

Сначала исключаются завершённые, просмотренные события и другие города. Затем score: город +5, выбранная категория +3, бюджет +2, подходящий день +1, время +1, семейные теги +2. История реакций по категории добавляет/вычитает 2 за каждую реакцию (до трёх). При одинаковом score раньше показывается ближайшее событие. Компания учитывается для семейных тегов; источник не предоставляет универсальную разметку для всех типов компании. Алгоритм изолирован в `RecommendationService`; frontend получает причины рекомендации.

## Разработка без Docker

### Архитектура backend

Backend разделён на три слоя:

- `app/transport/api` — HTTP-роутеры, Pydantic-схемы, авторизация запросов и перевод бизнес-ошибок в HTTP-ответы. `app/transport/integrations` — адаптеры Culture, демоисточника, MAX и JWT.
- `app/service` — бизнес-сервисы, независимые dataclass-сущности, команды, результаты и интерфейсы хранилищ, интеграций и часов. Слой не зависит от FastAPI, SQLAlchemy или внешних клиентов.
- `app/repository` — SQLAlchemy-модели, запросы и Unit of Work. Репозитории возвращают бизнес-сущности, доступные после закрытия сессии; ORM-объекты остаются внутри слоя.

`app/bootstrap.py` связывает реализации интерфейсов. Точка входа сохраняется: `app.main:app`. Один HTTP-запрос получает один Unit of Work; стартовая синхронизация использует отдельный. Сервисы определяют границы транзакций, а Unit of Work выполняет commit, rollback и закрытие сессии. Репозитории выполняют запросы и flush без самостоятельного commit. Предпочтения, город и завершение анкеты сохраняются одной транзакцией.

Преобразования на границах перечисляют поля явно: HTTP-запрос → команда service → репозиторий → ORM; ORM → сущность service → результат → HTTP-ответ. Мапперы находятся в соответствующих слоях, коллекции копируются. Схема БД, история миграций и контракт API сохранены; frontend и алгоритмы персонализации не менялись.

### Локальный запуск

Python 3.13+, Node 22+. SQLite поддерживается только для локальной разработки и тестов; Compose использует PostgreSQL.

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
export DATABASE_URL=sqlite+aiosqlite:////tmp/murshrut.db
export DEMO_MODE=true
export EVENT_PROVIDER=demo
.venv/bin/alembic upgrade head
.venv/bin/uvicorn app.main:app --reload
```

В другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Vite проксирует `/api` на backend:8000. Изменения схемы БД оформляются миграциями Alembic, начальная миграция применяется автоматически при запуске контейнера.

## Проверки

```bash
backend/.venv/bin/pytest backend/tests -q
cd frontend
npm run build
npx playwright install chromium
npm run test:e2e
```

Браузерные тесты ожидают запущенный демо Compose на localhost:8080. Тесты API проверяют подписанные MAX-данные и используют изолированную тестовую БД; браузерные тесты используют демопрофиль и изменяют его настройки/реакции.

Backend-тесты включают сервисы с подставными интерфейсами и управляемыми часами, явные преобразования сущностей, атомарность транзакций, доступность результатов после закрытия сессии и автоматический запрет импортов между слоями. По умолчанию проверки repository выполняются на SQLite. Для PostgreSQL укажите отдельную тестовую базу (проверки создают и удаляют собственную схему):

```bash
TEST_REPOSITORY_DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/test_db \
  backend/.venv/bin/pytest backend/tests -q
```

Совместимость моделей с существующими миграциями проверяется из `backend` командами `.venv/bin/alembic upgrade head` и `.venv/bin/alembic check` с настроенным `DATABASE_URL`. Ограничения источника, выбора одного сеанса и персонализации остаются описанными выше. После успешной полной синхронизации отсутствующие в ответе события помечаются неактуальными в пределах источника и города (для демо — всех демогородов). Они скрываются из каталога, рекомендаций, избранного и подробностей, но записи и реакции сохраняются. Повторное появление восстанавливает событие с прежним ID. Обновление и деактивация выполняются одной транзакцией. Ошибка загрузки любой страницы или некорректный ответ не деактивируют кэш. Новое поле `events.is_active` добавляется миграцией Alembic; перед запуском обновлённого backend выполните `alembic upgrade head`.
